BondWatch 技术路线

修订稿 v1.1 · 语音对照 ESP32.AI / YunDo， 表盘对照 OV-Watch（STM32 + LVGL，不整包烧入）。 关联：看板 · 软件与 UI · 2D 表情动画 · 云端交付

一句话 手表只做眼睛和嘴巴；语音像 YunDo 一样走 MQTT → 识别 → 大模型 → 合成。 表盘、触摸、手势继续用已经跑通的 Arduino / PlatformIO，不改成 MicroPython。

1. 从 YunDo 学什么、不学什么

学（语音骨架）

  • ESP32 只采集 / 播放声音，不跑大模型
  • 音频用 MQTT 传到 Python 服务端
  • 服务端拆成：语音转文字 → 大模型 → 文字转语音
  • Broker 用 Mosquitto（本机 Docker）或 EMQX（上线）
  • 厂商可替换：YunDo 用 Azure + Dify；我们用国内 API，主题名不变

不学（会推倒已有表）

  • 不刷 MicroPython / Thonny — 240×320 表盘、CST816 校准、横竖屏已是 C++
  • 不绑死 Azure、不强制 Dify 中间层
  • 不把表做成「只有喇叭的语音盒子」— BondWatch 还有表盘和控制
  • 绑定、记忆、假手表文字回合仍走 FastAPI HTTP

1b. 从 OV-Watch 学什么、不学什么

不能把 OV-Watch 固件直接烧进 BondWatch 那是 STM32F411 + Keil + LVGL 8.2 工程。我们是 ESP32-S3 + PlatformIO。 屏和触摸芯片碰巧同类（ST7789 + CST816），所以学的是驱动思路和「页面栈」这种小系统结构，不是拷贝 Keil 工程。 OV-Watch 是 GPL-3.0：整页复制他们的 GUI_App 会把本仓库也变成 GPL。只借鉴结构，界面自己写。

学

  • LVGL + 页面栈 = 腕上「小系统」手感（Home → Menu → App → 返回）
  • CST816：I2C 轮询坐标即可，INT 不是必须；FingerNum=0xFF 表示休眠
  • 硬件中间层（他们的 HWDataAccess）：UI 不直接碰引脚，方便 PC 仿真
  • 秒表 / 计算器 / 设置列表：作为 BondWatch 自己的页面以后加

不搬

  • STM32 HAL、Keil、Bootloader、蓝牙 KT6368A OTA
  • MPU6050 抬腕、心率 EM7028、指南针、气压计、NFC（我们板子没有）
  • 他们的 1.69 寸 240×280 LVGL 屏幕资源（我们是 2.0 寸 240×320）
  • 不把 BondWatch 改成运动健康表；伴侣 + MQTT 语音仍是主线

2. 分层

手表 Arduino（显示 / 触摸 / 键 / I2S）
        │  控制面 HTTP：登录、设置、记忆、文字回合
        │  媒体面 MQTT：上行 PCM，下行 TTS + 情绪
        ▼
+------------------+     +------------------+
| FastAPI :11111   |     | Mosquitto :1883  |
| 账号 / 设备 / 记忆 |     | 语音主题总线      |
+--------+---------+     +--------+---------+
         |                         |
         +-----------+-------------+
                     ▼
              Python worker
         STT → LLM → TTS
         火山 / 阿里 / Azure 可换
                     │
                     ▼
              下行 MQTT：emotion 先到，再音频

3. MQTT 主题（冻结）

主题方向内容
bw/{device_id}/up/audio表 → 云PCM 16 kHz / 16-bit / 单声道（以后可改 opus）
bw/{device_id}/up/ctrl表 → 云JSON：end / interrupt / ping
bw/{device_id}/dn/meta云 → 表JSON：先 emotion=think|speak，再 reply_text
bw/{device_id}/dn/audio云 → 表TTS 音频帧；必须晚于对应 emotion

假手表、手机、电脑用同一个 device_id 会话。持麦仍由 FastAPI session 裁定；MQTT 只运音频和表情。

4. 两套接口怎么分工

面协议干什么不干什么
控制面 HTTP FastAPI :11111 登录、绑定、设置、记忆、文字 /turn、闹钟配置 不传实时麦流
媒体面 MQTT 1883（演示可 9001 WebSocket） 采音、放音、打断、情绪包 不做人设和记忆存储
4G Air780E 上 MQTT（Wi‑Fi 不通时） 同一套主题 不在模组里跑识别
为什么不用表直连 WebSocket 音频 YunDo 和 Air780E 都更吃 MQTT：弱网重连、4G 模组原生、主题好调试（MQTTX 冒充手表）。 旧方案 WS /v1/sessions/{id}/audio 作废，改走上面四条主题。

5. 固件与云怎么落地

阶段表云验收
现在 · 表盘壳 VOICE_FEATURES=0，Arduino UI FastAPI + Postgres 已有；Docker 起 Mosquitto MQTTX 能连 :1883 收发一条
语音闭环 I2S 采播 + MQTT 客户端（仍 C++） worker：STT → DeepSeek → TTS 说完到第一包音频 p50 ≤ 1.5 s；表情先于声音
外出 4G S3 UART 把 MQTT 交给 Air780E，或 S3 自己经 4G 上网 同一 Broker 断 Wi‑Fi 仍能一轮对话

6. 表盘表情：2D 精灵（已拍板）

真表只做 2D，3D 仅作制作工具 ESP32-S3 无 GPU，交付格式是预烘焙 RGB565 精灵帧（160×176，8–12 fps）。 可选从 Three.js 烘 GLB，也可用 AI / 手绘直接出 sprite sheet。 优先换素材，不轻易改固件。 
素材（PNG 序列 / AI 视频抽帧 / 3D 烘焙）
  → scripts/pack_lumi_frames.py
  → firmware/src/lumi_frames.rgb565
  → bw_ui.cpp 按 clip 循环播放

AI 驱动三层：
  emotion（FSM：listen/think/speak）← 客户端本地
  expression（happy/shy/…）         ← LLM 结构化输出（规划）
  action（wave/nod/…）              ← LLM 从有限目录选（规划）

完整规格、内存预算、AI 工具清单、分阶段路线见 bondwatch-2d-animation.html。
